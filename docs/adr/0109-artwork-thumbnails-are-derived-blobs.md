# 0109. Artwork thumbnails are derived blobs; `?size=` names a bucket

**Status:** Accepted (2026-10-12)
**Date:** 2026-10-12
**Supersedes clause:** ADR-0075 "Revisit when — poster bytes cost too much on a real library"
**Builds on:** ADR-0005 (BLAKE3 identity), ADR-0008 (durable jobs), ADR-0013 (blob contract), ADR-0018 (logical delete / GC), ADR-0074 (guest boundary), ADR-0075 (artwork redirect shape)
**Tracks:** #741

## Context

ADR-0075 deliberately shipped with no `?size=` and a revisit clause: "If a phone
fetching a 4 MB scan for a 200 px card is what a real shelf looks like, an image
library and a content-addressed thumbnail cache earn `?size=`."

That trigger has fired. Measured 2026-10-12 on a library of 3,711 works from a
phone: card thumbnails arrive as full originals via `GET /blobs/{hash}/content` at
0.3–2.1 MB each (representative samples: 1,422,803 / 2,099,504 / 1,379,865 bytes)
for ~200–300 px cards; one detail screen fetches 12 images ≈ 9 MB. The redirect
shape in ADR-0075 is correct and survives this change; what changes is where it
redirects when a size is requested.

## Decision

**Add a `?size=` bucket parameter to the artwork redirect. A bucketed thumbnail is
a derived blob, identified by its own BLAKE3 hash (invariant 1), generated by a
durable idempotent job (invariants 4/9), and GC'd with its source (invariant 8).**

1. **Buckets, not pixel counts.** `?size=` accepts one of `256`, `512`, `1024`
   (long-edge pixels in the JPEG output). Arbitrary sizes are rejected with 400.
   A fixed set keeps the derived-blob table small (one row per source × bucket),
   prevents cache-key explosion, and removes the DoS surface of on-demand
   image processing at arbitrary sizes.

2. **A thumbnail is a derived blob.** `derived_thumbnails` records
   `(source_hash, bucket) → thumb_hash`, where `thumb_hash` is the BLAKE3 of the
   resized JPEG and a normal row in `blobs`. The artwork redirect without `?size=`
   is unchanged. With `?size=<bucket>`, it 307s to
   `/api/v1/blobs/{thumb_hash}/content` when the thumbnail is ready; while the job
   runs it 307s to the original (the current behavior), so the client gets the
   full blob on the first request and the thumbnail on subsequent ones. A 202
   would require a new retry contract on a GET; the 307-to-original keeps the
   existing redirect-following logic intact and makes the transition invisible to
   clients that have not yet adopted `?size=`. The `artwork` embed
   (`include=artwork`) gains `sizes`, a map of bucket → that redirect URL, because
   first-party clients read the embed's `content_url` and fetch the blob directly;
   without it they would never reach the redirect.

3. **Thumbnail generation is a durable, leased, idempotent job.** Job kind
   `derive_thumbnail` carries `(source_hash, bucket)`. The handler decodes the
   source JPEG, PNG, or WebP; scales it with a Catmull-Rom kernel
   (`golang.org/x/image/draw`, pure-Go, CGO-free) so the long edge is at most
   `bucket` pixels; encodes the output as JPEG (stdlib `image/jpeg`); stores the
   result in the CAS; and writes `thumb_hash` to `derived_thumbnails`. Re-running
   the job for the same `(source_hash, bucket)` that already has a `thumb_hash`
   is a no-op (invariant 9). AVIF and HEIC cannot be decoded without a CGO
   library; the job records the source as un-decodable, the route falls back to
   the original blob permanently, and no further attempt is made. Before a full
   decode the handler reads only the header (`image.DecodeConfig`) and records
   any source whose declared dimensions or byte size exceed fixed limits as
   un-decodable, so a small file declaring huge dimensions cannot exhaust the
   worker. A JPEG's EXIF orientation is applied before scaling, because
   re-encoding drops the tag and would otherwise turn phone-shot artwork sideways.
   Every transition — a thumbnail becoming `ready`, a source recorded
   `undecodable`, a derivation row removed with its source — emits its event in
   the same transaction as the row write (invariant 7).

4. **Guest boundary.** A thumbnail is only generated for a blob that is already
   reachable by the requesting caller. The artwork picker (ADR-0075) already
   filters vault assets to 404 for a Guest (ADR-0074); the thumbnail route
   inherits the same check. The server never generates thumbnails for vault
   (encrypted personal-state) blobs server-side: encrypted ciphertext is opaque
   to the server (invariant 6) and would produce a useless output even if
   attempted.

5. **GC, one way.** A `derived_thumbnails` row references its thumbnail blob
   only; it is never a reference to the source. When the source is logically
   deleted or reclaimed, its derivation rows are removed in that same step, the
   thumbnail loses its only reference, and the ordinary grace-window sweep of
   ADR-0018 reclaims it (invariant 8). Nothing is unlinked inline.

6. **Cache headers.** The derived blob is served with
   `Cache-Control: public, max-age=31536000, immutable` — correct because the URL
   is the BLAKE3 hash (ADR-0013). The ready and un-decodable redirects keep the
   existing `private, max-age=300`, so a work whose source artwork changes is
   re-checked. The pending redirect (307 to the original while the job runs) is
   `no-store`: caching it would keep a client on the full-size original after the
   thumbnail is ready.

**Accepted with these defaults (2026-10-12):**
- one `derived_thumbnails` table, keyed by `(source_hash, bucket)`, with a `status`
  column (`ready` | `undecodable`), not a separate errors table;
- first-party clients request `256` for cards and rails and `512` for a detail hero;
  `1024` is for large screens;
- pending stays a 307 to the original (above), never a 202.

## Consequences

- Card and detail-screen thumbnail fetches drop from 0.3–2.1 MB to roughly
  8–25 kB once the first request has triggered generation.
- The CAS grows by one derived JPEG per work × bucket requested; the set is
  bounded and computable.
- The OpenAPI spec gains `?size=` on the artwork redirect routes;
  heyarr-kmp adopts it in a follow-up change.
- Formats the server cannot decode (AVIF, HEIC) fall back to the original
  permanently; no silent failure, no partial cache poisoning.
- The `golang.org/x/image` module is a new direct dependency (pure-Go, no CGO).

## Revisit when

- A pure-Go AVIF or HEIC decoder becomes available and maintained — at that
  point the un-decodable fallback can be lifted for those formats.
- WebP or AVIF output reduces thumbnail bytes further than JPEG at acceptable
  quality — the bucket table and the job handler can be extended; the URL shape
  is unchanged because the hash absorbs the format difference.
- The `derived_thumbnails` table grows large enough to warrant a cleanup sweep
  for buckets no client has requested in over a year.
